# Providers & Model Aliases

Set via `hermes model` (picker) or `hermes setup`. 35+ provider profiles ship as
plugins under `plugins/model-providers/`; user plugins of the same name override.
Full docs: https://hermes-agent.nousresearch.com/docs/integrations/providers

### User-defined model aliases

Work with `/model <name>` in CLI and every gateway platform. Resolved by
`hermes_cli/model_switch.py::resolve_alias()`; user aliases are checked BEFORE
the built-in table, so a user `sonnet`/`grok` shadows the built-in.

```yaml
# Full form
model_aliases:
  fav:
    model: claude-sonnet-4.6
    provider: anthropic
  local-qwen:
    model: qwen3.5:397b
    provider: custom
    base_url: "https://ollama.com/v1"
  theta:
    model: theta-1
    provider: custom
    base_url: "https://theta.example.com/v1"
    key_env: THETA_API_KEY        # or: api_key: "${THETA_API_KEY}"

# Short form ("provider/model"), also via CLI:
#   hermes config set model.aliases.fav openrouter/anthropic/claude-sonnet-4.6
model:
  aliases:
    fav: openrouter/anthropic/claude-sonnet-4.6
```

`/model fav` — session-scoped; add `--global` to persist as default.

### Switching a different active messaging chat

For a custom provider plugin, use `/model <model-id> --provider <plugin-id> --session` in the target chat. Do not assume the documented `provider:model` shorthand recognizes custom plugins: on the inspected installation, `agent-router:gpt-6-astra` resolves as model `agent-router/gpt-6-astra` on the CURRENT AnyModel provider and fails validation; `gpt-6-astra --provider agent-router --session` resolves correctly to Agent Router with `codex_responses`. A Telegram switch does not switch the separate MAX session. Distinguish the default config, a per-channel override, the persisted session override, and the live cached agent.

Before recommending an alternative command after a failed switch, reproduce its parsing with `hermes_cli.model_switch.parse_model_switch_args` and resolve it with `switch_model(..., is_global=False)` in the installed Hermes runtime. This resolves the selection without applying it; print only success/model/provider/api_mode/error fields, never credentials. A reply containing raw i18n keys such as `gateway.model.error_prefix` hides the real error; inspect the resolver's `error_message` rather than treating the key as the cause. Read MAX command messages and their replies through `GET /messages`, never start a second `GET /updates` consumer. Filter unrelated user messages before printing history because they can contain secrets.

Do not edit `sessions.json`, `state.db`, or session model metadata from another process and claim the running chat switched: the gateway also caches its routing entries, model overrides, and agents. Verify a supported live update path before writing. Likewise, `rescan-profiles` is not a general configuration reload: the inspected implementation excludes the primary active profile from config-change rescans.

If no supported cross-chat live switch is available, say so promptly and provide the target-chat command rather than spending many discovery rounds or restarting all messaging for a small model change. After an actual change, read the exact target back; claim a successful model response only after a real turn.

An alias with its own `base_url` authenticates with its own credential
(`api_key`, which also accepts a `"${VAR}"` reference, or `key_env`). With
neither set the key is resolved from the alias HOST, never carried over from
the provider that was active before the switch.

Built-in aliases (catalog-resolved against the active provider): `sonnet`,
`opus`, `haiku`, `claude`, `gpt5`, `gpt`, `codex`, `o3`, `o4`, `gemini`,
`deepseek`, `grok`, `llama`, `qwen`, `minimax`, `nemotron`, `kimi`, `glm`,
`step`, `mimo`, `trinity`.
