# QA-Agent — automated QA for Георгия's production products

Класс-задача: автоматическая проверка продакшен-бобов и панелей (Telegram/MAX-боты, веб-модули, n8n), конвейер версий.

## When to use

- «запусти QA-агента» / «прогай QA» — проверка живых сервисов по сценариям, отчёты
- проверка нового n8n-воркфлоу/билда перед релизом (deploy-агент использует)
- интеграционный ско-мок тест подключенных подсистем

## How to do it, in order

1. **Собери точный контекст, не гадай.** Проверь: адреса сервисов, токены в /root/.secrets/ (n8n.env, supabase.env), порты (beef-app :8101, manicure :8099, nginx vm), куски схем. Логгируй в output/qa-agent.log.
2. **Собери сценарии.** Каждый сценарий = тест-файл Python в api-tests/, импортирующий helpers.py. `helpers.py` — общий клиент-модуль, а НЕ тест: раннер обязан его исключать (`NON_TEST_MODULES`), иначе он «пройдёт» вхолостую и засорит отчёт. Пиши сценарии, которые ассертуют то, что ДЕЙСТВИТЕЛЬНО верно для твоих систем, а не то, что ты *ожидаешь*. Сначала прогони быстрый probe, потом тесты.
3. **Запусти сценарии как подпроцесс** из run_qa.py: `python3 run_qa.py` (все api-tests/*.py, кроме helpers.py), `python3 run_qa.py api-tests/<file>.py` (один), `python3 run_qa.py --list`.
4. **Логгируй каждый шаг** в output/qa-agent.log (INFO), подробности — в выводе сценария.
5. **Генерируй отчёт** в output/reports/qa-<ts>.json + *.html: файл, rc, PASS/FAIL, вывод.
6. **Browser-тесты запускай через `browser_exec`** (не через subprocess) — помощники есть только там. Каждый браузерный сценарий — отдельный .py в browser-tests/, печатает JSON-отчёт.
7. **Интерпретируй результаты как данные, не как вердикт.** Не пытайся обмануть тест: если тест упал по простой причине — это слабость теста, зафиксируй. Для Supabase: `select=count` без FROM запрещён PostgREST (PGRST100) — это ожидаемое на этой стэке, зафиксируй как INFO, не падай.

## Standing rules (always-on)

- **Выбирай интерпретатор явно.** `python3` в PATH резолвится в bundled-питон Hermes (`/root/.hermes/tools/python-*/bin/python3`), где НЕТ `requests` — любой тест падает с `ModuleNotFoundError: No module named 'requests'`. Раннер должен перебирать кандидатов (`/usr/bin/python3`, `/usr/bin/python3.12`, `python3`) и брать тот, где `import requests` проходит. Проверяй это до написания тестов, а не после.
- Порты и адреса — в operational notes, не в коде. Кэшируй коротко, обновляй при изменениях.
- Переменные, куски, логи — английские. Клиентский вывод на русском.
- Никаких секретов в коде и в отчётах: /root/.secrets/ (700, файлы 600). Только пути.
- Выходной каталог: output/reports/, output/screenshots/, output/qa-agent.log.
- `browser_exec` — первый браузерный инструмент. Если его демон зависает (`Page.navigate timed out`, IPC timeout), не жди: гоняй node-Playwright из уже установленного `node_modules` проекта — `NODE_PATH=<project>/tests/frontend/node_modules node script.js`. Python-playwright в системном питоне при этом всё равно отсутствует, ставить его не нужно.

## Проверка только что опубликованного маршрута

Новый сервис за nginx проверяется не «страница отдала 200», а цепочкой ниже. Каждый пункт — отдельное доказательство.

- **Hairpin NAT: curl с самого сервера к своему публичному домену висит по таймауту.** Это не сломанный деплой. Проверяй через loopback с настоящим Host/SNI: `curl -sS --resolve <host>:443:127.0.0.1 -o /dev/null -w '%{http_code} %{content_type}\n' https://<host>/<path>/`. Отдельно докажи сертификат (`openssl s_client -connect <host>:443 -servername <host> -verify_return_error`, `Verify return code: 0`) и что имя вообще указывает на эту машину (`dig @8.8.8.8 +short <host>`). Без этих двух проверок «curl упал» легко перепутать с «не опубликовано».
- **Браузер на публичный маршрут — через resolver map, без правки /etc/hosts.** `chromium.launch({args:['--no-sandbox','--host-resolver-rules=MAP <host> 127.0.0.1']})` даёт настоящий TLS, настоящий CSP и настоящий nginx-префикс. Ассерть состояние, а не скриншот: наличие данных приложения в `window`, количество элементов, ноль ошибок консоли и `pageerror`, `scrollWidth <= clientWidth + 1` на мобильной ширине.
- **Соседи — снимок до и после reload, дифом.** Все маршруты из baseline-файла плюс `/`. Любое изменение статуса = откат конфига. Если расхождение нашлось, сначала проверь, не было ли оно ДО деплоя (сравни с прошлым readiness-отчётом): редирект на `/` из-за корневого прокси легко приписать своему изменению.
- **Платный провайдер подключай отдельной фазой, после того как сервис доказан без ключа.** Сначала сервис стартует и работает с `ai_enabled:false` — тогда сбой имеет одну причину, а не две. Потом ключ в env-файл сервиса и restart.
- **После restart опрашивай health в цикле, не читай первый ответ.** Первый запрос может попасть в старт и вернуть 503 — это не регрессия: `for i in 1 2 3 4 5; do curl .../api/health && break; sleep 2; done`.
- **Считай, сколько попыток квоты съела сама проверка**, если у фичи дневной лимит, и назови владельцу реальный остаток: его проверка тратит тот же бюджет, что и клиент.
- **Секрет не должен оказаться в дереве релиза.** Прогон по файлам релиза на байты ключа возвращает только булевы значения и пути, без значения: `release_clean: true`.

## When you get stuck

- если тест падает из-за отсутствия модуля/сервиса — не печатай предупреждение, зафиксируй исправление или оставь как есть с понятным логом.
- если браузерный скрипт не проходит через subprocess (из-за browser_exec), запускай его напрямую в browser_exec.
- если Supabase отвечает 400 PGRST100 на `select=count` — это не ошибка теста, а стэк; зафиксируй INFO.
- **Упавший тест — это находка, а не повод править ассерт.** Сначала проверь эндпоинт живьём (`curl`/`requests`) и реши, кто неправ — тест или система. Правь ассерт только когда доказано, что expectation неверное (напр. healthz открыт по дизайну). Ослабить тест до PASS — значит потерять находку.
- **Настоящая дыра почти всегда в catch-all прокси, а не в отдельных роутах.** Когда ищешь незащищённые эндпоинты, смотри в первую очередь на роут-заглушку вида `/api/supabase/**`, которая ходит в БД **с привилегированным ключом** (service_role / admin) и без проверки актора. Такой роут отдаёт любую таблицу анониму, и в логах он выглядит как обычный 200. Отдельные роуты вроде `/stock` при этом могут быть **открыты по дизайну** (фронт зовёт их на `DOMContentLoaded` до идентификации) — закрывать их = сломать приложение. Проверяй сначала прокси, потом роуты.
- **Прежде чем называть открытый роут «утечкой» — проверь, как его использует фронт.** Вызов на загрузке страницы до авторизации означает, что роут публичный намеренно. Ассерть для таких надо **достижимость** (иначе упавшее приложение останется незамеченным), а не закрытость.
- beef-app слушает `:8101` (systemd `beef-app.service`); `:3900` — чужой контейнер (`vs-test`). Не путай порты.
- **n8n REST на этом хосте не стоковый:** `/n8n/workflows` и `/n8n/executions` проксируются в веб-морду (200 + HTML-шелл), JSON отдаёт только `/n8n/healthz`. Наличие API по коду 200 не проверить — 200 приходит и за HTML. Смотри на тело ответа, а не на статус.

## Deepen when needed

- если нужны бизнес-юнит-тесты подключенных модулей — прочитай о паттернах в `supabase-crud-patterns`.
- если нужно подробнее протестировать веб-интерфейс — `dogfood` (DOM-проверки, скриншоты, рейтинг индикаторов).
- если сценарии начинают зависеть от состояния БД — прежде чем добавить сценарий, убедись, что схема применима и данные воспроизводимы (backup состояния, reset after test).
- точные адреса, порты и реальные ответы живых сервисов — в `references/live-surface.md`.
